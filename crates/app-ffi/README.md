# Phone bridge

`app-ffi` is the C ABI the iPhone app calls. It hosts two crates:
`app-embedded`, the daemon running in the app's own process as one
installation with one profile per account (each with its store of replica
rows, identity, pairing and relay link), and `app-runtime`, the chats and
fleet over one of those profiles. Nothing outside this
crate knows a C type exists; the header is generated by cbindgen into the
build's `OUT_DIR` as `amux_app.h`.

## Values

Everything crosses as JSON. The Swift mirrors of every value are generated
from the Rust definitions into
`apps/apple/Packages/AmuxCore/Sources/AmuxValues/Values.swift`:

```sh
cargo run -p ios-tools -- swift-types          # regenerate
cargo run -p ios-tools -- swift-types --check  # fail when the committed file differs
```

Rows, ask cards, the overview and fleet cards are the `ui-view` values the
terminal renders; `ChatFrame`, `ChatChanges`, `Draft`,
`HostView` and the act outcomes are `app-runtime::values`. Byte strings such
as agent and input ids are JSON arrays of numbers. Answers never carry a
provider's answer body: the phone names a choice by its position on the
card, gives one `QuestionResponse` (a `Pick` and a note) per question, or
gives a form one `FormValue` per field, and the answer is built in Rust.

## Lifecycle

```c
AmuxRuntime *rt = amux_runtime_start(config_json, &error);
int fd = amux_runtime_wake_fd(rt);                   /* watch for readable */
char *stepped = amux_runtime_step(rt);               /* on every wake */
AmuxProfile *p = amux_profile_open(rt, profile_id, &error);
AmuxChat *chat = amux_session_open(p, agent_key_json, 0, &error);
...
amux_session_close(chat);
amux_profile_close(p);
amux_runtime_stop(rt);
```

The app owns the loop. Every profile's daemon core steps on the queue that
calls `amux_runtime_step`; links, channels and gRPC run on one confined Rust
thread, which posts what it decodes onto the cores' queues and never calls
into the app. Whenever something waits for a step, the descriptor
`amux_runtime_wake_fd` answers becomes readable; the app watches it from the
queue it steps on. A step answers JSON: `profiles` (every profile as
`[ProfileView]`, oldest first, when the list moved: once the registry is read
after the start, and before the answer of any act that moved it), `fleets`
and `chats` (each the fleet's number and a `FleetDelta` or `ChatDelta`: what
moved in that view, see below) and `answers` (each an act's ticket and its
result as JSON text, after the deltas of what the act moved).

`amux_runtime_start` takes a `StartConfig` and blocks until every profile's
store is open. Every call that blocks until the cores have done something
steps them on the calling thread while it waits, so it may be made from the
queue that steps. `amux_profile_open` opens one
profile's fleet and blocks until it has caught up with that profile's store;
the app keeps only the profile on screen open. `amux_session_open` blocks
until the chat's snapshot and the rows this device holds are applied, so its
opening is whole even with the agent's host away. Close every chat
before its profile, and every profile before stopping the runtime.

## The profile registry

The installation's registry, by profile id, each an act answering under its
ticket: `amux_runtime_create_profile`, `amux_runtime_delete_profile` (the
installation keeps at least one), `amux_runtime_bind` (a sign-in's refresh
token with the OAuth client it was issued to; a named profile is adopted even
when it paired machines before, null lets the registry pick the account's own
profile, else one that holds nothing, else a new one), `amux_runtime_sign_out`
(the profile stays tied to its account), `amux_runtime_access_token` (a
bearer for the account service; the profile alone spends the refresh token),
`amux_runtime_refresh_entitlement` (asks what the account buys now, so a
purchase lifts the relay's tier at once) and `amux_runtime_trusting_profiles`
(every profile whose trust store holds a host, oldest first); a driving build's
`amux_runtime_offer_pairing` opens pairing mode on a profile and answers its
pairing link, so tests can pair two profiles. `amux_runtime_discovered` hands
the whole set the phone's own browser found on the local network, which only
the system may browse, to every profile.

`amux_runtime_list_sources(rt, profile)` keeps a source open for every listed
agent of the profile on screen, and only for the chats that open for every
other profile; null, for the app in the background, lists none.

Product analytics ([what is sent](../../docs/ANALYTICS.md)) is the
runtime's; the app tells it what only the app knows.
`amux_runtime_set_telemetry(rt, on)` follows the app's Share Usage setting
(the start's `StartConfig.telemetry` is its first value), and off holds back
what is waiting too. `amux_runtime_set_auto_reports(rt, on)` follows the
app's Send Automatic Reports setting (first value `StartConfig.auto_reports`):
whether a dump a check takes is sent to the account on its own.
`amux_runtime_feed(rt, input_json, &error)` feeds the
app's life as a `Lifecycle`: `"Foreground"` says the app came to the front,
counted at most once an hour; `"Background"` sends what is waiting, for a
few seconds at most, before it returns; `"Suspending"` does too, then
checkpoints every profile's core at a passive WAL checkpoint of its store and
returns once each checkpoint is on the drive; `"NetworkChanged"` binds every
profile's link socket afresh, so its links move to the new network with
their QUIC connections, tells every path machine to probe its paths again,
and writes a `rebind` line to the link log saying so. `amux_runtime_record(rt, profile, event_json)` records a
`UsageEvent` (the paywall opening, a purchase starting) on that profile, or on
every profile when `profile` is null. Only a published build sends; every
other build records nothing unless `AMUX_ANALYTICS_URL` names a server.

## Views and deltas

A fleet and a chat each open with the whole of what they show, and then
hear what moved. `amux_fleet_opening(profile)` answers a `FleetDelta` with
home's sections and every host; `amux_session_opening(chat)` a `ChatDelta`
with every key, the frame, the head ask, the overview and the settings. No
step hands over a delta for either before its opening. After it, a step
carries a delta for each that moved, with only the fields that moved, and
at most one per view: however many updates land in between, the host hears
them together. Nothing closed is handed over again.

A chat's rows are handed out by item key, which never moves, so its
`sequence` changes only at its two edges until it reloads: `Edges` names the
keys newer than the newest the host holds, a page of older ones below its
oldest, and how many of its oldest the window dropped (while the reader
follows the newest row, the window keeps at most its cap). `Reload` hands
over every key. A delta's `rows` are the rows that changed among those the
host held; a row new at either edge, or held through a reload, is read with
`amux_session_rows_for` when it is drawn.

What a view folds is held in Rust, so a read needs nothing passed in: a chat
draws each run folded to its newest step until `amux_session_toggle_run`
opens it, and keeps an open run open as it grows, pages in older steps or
trims its oldest; a fleet lists a family's members under its root once
`amux_fleet_toggle_family` opens it, narrowed by the last `amux_fleet_filter`.
Each change is handed over by the next step.

The host says where its reader is with `amux_session_follow(chat, following)`:
false when the reader leaves the newest row, true on the return. In history
the window stays put, arrivals are held apart and the frame's `arrivals_held`
says so; the return releases them, or reloads the newest rows when more
arrived than the window holds.

Other reads return at once: `amux_fleet_card`, `amux_fleet_family`,
`amux_runtime_source_policy_listed`. Some reads need
no handle, because they are the shared rules applied to values the phone
already holds: `amux_agent_name_problem` (why a name cannot name an agent),
`amux_new_agent_settings` and `amux_new_agent_pick` (a new agent's pickers
from a host's catalogue), and `amux_form_problems` (each field's
`FieldProblem` for a form's `FormField`s and the `FormValue`s entered).

## Acts

Acts that wait on the agent return a ticket at once (0 when the handle is
gone), and their JSON result comes back in a later step's answers under it:
`amux_session_send`, `amux_session_command` (a draft that may be one of the client's own commands or a refused one; the result says which), `amux_session_answer` (by choice index),
`amux_session_answer_questions`, `amux_session_reply_instead`, `amux_session_answer_form`
(one `FormValue` per field, checked and encoded in Rust), `amux_session_change_setting` (a pick from
the settings view), `amux_session_withdraw`,
`amux_session_send_now`, `amux_session_resend`, `amux_session_interrupt`, `amux_session_stop_job`, `amux_session_switch_back`,
`amux_session_resume` (the exited composer's draft), `amux_session_page_older`,
`amux_session_put_blob`, `amux_session_open_overview` (the changed files for
a `Comparison`, fetched without a patch as the overview opens),
`amux_session_review` (the diff for a `Comparison` and its patch, frozen for
the review page), `amux_profile_host_catalogue` (what a provider offers on a
host with no agent running, for the new-agent screen),
`amux_profile_begin_pair` (a PIN or a pairing
link: reaches and authenticates the machine, answering its name and
fingerprint), `amux_profile_confirm_pair` and `amux_profile_abandon_pair`
(the person's decision), `amux_profile_unpair`, `amux_profile_roster` (this
device's identity in the profile and the machines it trusts),
`amux_profile_account` (the binding and the relay link),
`amux_profile_create_agent`, `amux_profile_directories`,
`amux_profile_agent_act` (rename, stop, delete), `amux_profile_dump` (with
`for_report`, the narrower dump a person's report carries) and
`amux_profile_submit_report` (writes the report around that dump and sends
it, answering a `ReportSent`).
`amux_session_discard` forgets a not-confirmed input at once, and
`amux_profile_set_foreground(profile, foreground)` closes every agent's
stream as the app leaves the foreground and reopens them on its return.

## Ownership

Every returned string is the caller's to free with `amux_string_free`, and
every `AmuxBytes` with `amux_bytes_free`. A null return means the call
failed; a panic inside the library is caught at the boundary and reads as a
failure. The `debug-tools` feature, which only driving builds carry, lets
`StartConfig.lan_bind` keep direct links on loopback.

## Tests

`cargo test -p app-ffi` drives the C functions against a desk served in
process: pairing by PIN, the fleet, a chat's rows by key, a permission
answered by position, a question answered with picks, paging and a dump, and
the profile registry (create, the list moving, per-profile identity and source
policy, delete and the refusal to delete the last).
A confinement test holds the loop's shape: the header declares no function
type the library could call back through, and a step on one thread drains
the inputs another thread posted. `cargo test -p app-runtime` covers the
wake-once coalescing and the chat
views; `cargo test -p app-embedded` covers pairing on the local network,
sign-in with pairing through the relay, and one profile per account: binding
by id with adoption, a second account's own profile, pause and resume,
sign-out and signing back in, delete, and the trusting-profile lookup.

`just ios rust` builds the simulator slice with `debug-tools` and packages it
as `target/ios/AmuxAppDebugTools.xcframework`; `just ios package` builds every
shipping slice into `target/ios/AmuxApp.xcframework`.
